# Приёмка ручного доверия Host ↔ Client

Продолжение [настоящей DSH-приёмки](dsh-ocean-acceptance.ru.md). Проверены native DSH **0.2.0-rc.2** на bigpc и ноутбуке, а не fake Host API. Для новой стороны создан третий, полностью отдельный Client2 fixture с новыми HOME/DSH_HOME/XDG/CODEX_HOME и identity. Публичные package/dependency файлы можно переиспользовать; старые identities, profiles и model credentials в Client2 **не копировались**. Всё выполнялось обычным пользователем, только loopback, с собственным приватным Ocean.

## Проверенный результат

1. **Legacy migration.** Сохранённые Host/Client1 pins из предыдущего этапа загрузились и установили реальную Relay/Noise связь. Native workspace/follow вернул прежний подготовленный Host workspace. Обе стороны остались `legacy`, без фиктивного ручного provenance.
2. **Нет доверия при discovery.** Новый авторизованный Client2 увидел Host как `unknown`; просмотр не создал pin и даже pending. Попытка соединения создала только локальный pending Host, остановившись до запроса к Host. Host-side pending оставался пустым, Client2 connected=false.
3. **Настоящая local authority.** Аутентифицированные локальные HTTP-запросы на обеих машинах получили localApproval=true. Запрос с той же действующей test-cookie, но без Origin и с поддельным `localApproval:true` в payload, не подтвердил ключ. Неверный полный hash и старая generation тоже отклонены без pin.
4. **Реальный Client UI.** В новом отдельном системном Chrome открыта универсальная кнопка «Ключи». Отпечаток для ввода взят из **собственного Host control на другой машине через проверенный SSH**, а не скопирован из входящего запроса. Без checkbox, с коротким отпечатком или lower-case input кнопка подтверждения не включается. Точный SHA-256 плюс checkbox разрешили явный local-HTTP approval. Draft сохранился при ручном refresh той же generation; Escape закрыл диалог и вернул фокус; uncaught page errors=0.
5. **Host по-прежнему закрыт.** После первого pin новая попытка Client2 была отклонена Host. Host pending Device ID/full SHA совпали с собственным Client2 control; Host ещё не имел pin, Client2 connected=false. Независимые metadata-запросы native Remote UI тоже могут создать такой pending, но не обходят второе подтверждение.
6. **Preview deny — с точной границей доказательства.** Через уже работающий зашифрованный Client1 получен отказ `LOOPBACK_PORT_DENIED` на открытие Native app port Host при текущем **пустом allowlist**. Preview URL/HTTP к app не открылись, pin и generation не изменились. Случай «app port явно добавлен в allowlist, но protected getter всё равно запрещает его», control-prefix на любом порту и dynamic handle revocation проверены **unit-интеграцией с настоящим локальным HTTP/WS upstream**, не названы двухмашинным E2E. Изменение allowlist через настройки используемого CLI-overlay-профиля не было успешно выполнено; это не подменяется заявлением о native override-тесте.
7. **Реальный Host UI.** Открыт отдельный Host native Web через собственный loopback-only SSH-forward того же порта. Полный отпечаток введён из **собственного Client2 control на ноутбуке**. Та же строгая UI-проверка, manual provenance, refresh/keyboard/focus и ноль page errors подтверждены. В first-run dialogs выбрано Continue/Configure later: LLM keys не вводились.
8. **Доступ только после двух pins.** После обоих подтверждений явный Connect установил настоящую Noise/Relay сессию Client2 ↔ Host: transport=Relay, native remoteGateway=true. Native workspace/follow вернул прежний подготовленный workspace (1 запись). Disconnect подтвердил connected=false, новая связь снова прошла. Пины, trustedAt и provenance при этом не переписались; Client1 остался legacy.
9. **Не только memory cache.** Оба native процесса были штатно остановлены и заново запущены с другими kernel PID/birth. Из диска загрузились те же manual pins и trustedAt; повторные Relay/native API/reconnect проверки прошли. Приватные launch tokens при каждой остановке убирались из run records.

После финального restart-теста все три созданных DSH остановлены адресно, bootstrap URLs удалены из private run records. На обеих машинах owner leases=0 и indeterminate markers=0. Отдельный test SSH-forward закрыт; приватные fixtures и защищённая копия прежних test identities оставлены для воспроизводимости. Ocean healthz после очистки отвечает по валидному HTTPS, постоянный own route service active/enabled.

Ни существующий рабочий DSH, ни его profiles/dependencies, ни model API keys не менялись. Собственный постоянно работающий Ocean и его approved route service не останавливались. Независимый browser context не использовал cookies/профиль пользовательского Chrome; test-forward был отдельным SSH-процессом без общего ControlMaster.

## Автоматические проверки и ревью

- Полный plugin suite: **454/454 tests, 61 файл**; TypeScript check, build, bundle verification и diff hygiene пройдены.
- Новые проверки включают immutable pin/storage transaction/lease, exact full SHA, TTL/generation/bounds/cooldown, stale callback, неизвестные/изменившиеся ключи, passive discovery, lifecycle/revoke ordering, HTTP authority, поддельный RPC context, protected preview paths/ports, account/role transitions.
- Независимое read-only ревью foundation дало GO в рамках одного writer process и явного офлайн-восстановления. Отдельное integration ревью проверило fallback/local HTTP, endpoint routing, runtime replacement, исходный fetch и preview-политики. Runtime evidence выше получено отдельно основной приёмкой, не приписывается ревьюерам.
- После ревью добавлены regression cases account/QR transition + same-URL role replacement и включён QR start в сериализацию. Отдельно закрыт CLI lifecycle: каждый созданный IdentityStore обязательно закрывается на success/early-return/error, чтобы обычная команда не оставляла writer lease; 14 CLI tests входят в окончательные 454. Итоговое независимое ревью дало GO и самостоятельно повторило 35 scoped tests, включая все 14 CLI cases. Сам SDK rc.2 действительно игнорирует третий RPC authority argument; его опубликованный webServer.port действительно является OS-bound port после listen. Эти свойства проверены по установленному публичному SDK-коду, не выдуманы из structural TypeScript-типа.

## Ограничения

[Руководство](manual-peer-trust.ru.md) описывает local-only authority, различие Host/Client self-ключей, legacy provenance и owner-lease recovery. Один writer process на directory; mixed old/new writers, сетевые/shared каталоги и автоматическое восстановление после аварии не поддерживаются. После неопределённого filesystem commit нельзя обещать rollback: grant блокируется до офлайн-сверки. Pre-destructive reset-marker failures могут потребовать лишнего ручного восстановления, но не публикуют новое доверие.

Это не полный security/crypto/filesystem/OS audit. Не запускались платная LLM-генерация/полный chat-tool workflow, Codex/ACP, удалённый терминал, P2P/TURN и host/Docker-daemon reboot. Root/Docker admin либо уже получивший полный OS execution peer находится вне этой границы защиты. Другие мобильные/VS Code клиенты этой приёмкой не адаптированы.
