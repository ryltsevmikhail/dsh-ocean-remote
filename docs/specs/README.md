# Спецификации следующего функционального среза

Статус: **черновики для согласования, не разрешение на реализацию**.

Цель: довести Ocean + DSH Host/Client до воспроизводимого ежедневного сценария, затем обновлять дизайн на устойчивой функциональной основе. Спецификации описывают целевое поведение; наличие требования не означает, что оно уже реализовано или проверено.

Визуальный редизайн до закрытия функциональных сценариев не начинается; необходимые понятные ошибки и рабочие элементы управления входят в функциональные этапы.

## Границы версии

Обязательная платформа первой версии: Linux на двух реальных машинах, собственный Ocean через приватный Tailscale HTTPS, native DSH Host/Client. Проверенный ранее SDK — DSH 0.2.0-rc.2; целевая поддерживаемая версия фиксируется аудитом до реализации.

Не входят по умолчанию: отдельные Android/iOS, VS Code и standalone browser clients, публичный multi-user SaaS, платежи, SSO, новые model/backend интеграции, поддержка всех OS/SDK. Native DSH Web в браузере входит; это не обещание готовности отдельного standalone web client. Для Codex/ACP, терминала и P2P/TURN аудит обязан определить решение: включить в целевой релиз с отдельной приёмкой либо явно выключить и обозначить вне поддержки. Молчаливого обещания этих функций быть не должно.

## Исходные факты и неизвестное

[Предыдущая приёмка](../manual-peer-trust-acceptance.ru.md) установила работу Relay/Noise, native workspace API, локального двустороннего SHA-256 approval, reconnect и сохранения pins после перезапуска. Полный plugin suite на том срезе: 454 теста. Это историческая база, не свежий результат будущего среза.

Не доказаны полноценная LLM-сессия/tools, поведение при всех сбоях, безопасный upgrade/rollback и повседневная настройка без внутренних fixture helpers. CLI-overlay конфигурация и доступность native Plugins card требуют отдельной проверки. Действующая модель хранения имеет один writer process на identity directory и ручное восстановление после неопределённого commit; нельзя просто скрыть эти ограничения интерфейсом.

## Общие правила приёмки

1. Каждый этап: требования → реализация → автоматические проверки → реальный сценарий, где он требуется → независимое ревью → исправления → отдельный коммит.
2. Требования имеют ID. Матрица связывает каждый ID с тестом, результатом и доказательством либо явно открытым ограничением.
3. Unit с mock, интеграция с локальным upstream и двухмашинный E2E учитываются отдельно. Отсутствие ошибки в логах не равно успеху сценария.
4. Для каждого прогона фиксируются commit/artifact digest, SDK/Node/browser версии, topology, условия сети, шаги, ожидаемое/фактическое поведение и очистка. Секреты не входят в отчёт.
5. Рабочий DSH, его данные/ключи и существующие VPN/Tailscale настройки не меняются. Тесты — в отдельных приватных HOME/DSH_HOME/XDG/CODEX_HOME, обычным пользователем, без неявного импорта credentials.
6. Реальная модель, расходы, destructive tests и reboot требуют отдельного согласования условий. Авторизация планирования не разрешает автоматически использовать рабочие ключи или перезагружать host.
7. Security regression, несанкционированный доступ, тихая потеря/подмена данных и раскрытие секрета блокируют выпуск. Остальные дефекты получают приоритет, workaround и явное решение о выпуске.

## Классы приоритета и готовность

- **P0:** доступ без права, раскрытие секрета, потеря/подмена данных; соответствующий сценарий останавливается.
- **P1:** основной пользовательский путь не завершается или требует недокументированного обхода; блокирует функциональную готовность.
- **P2:** деградация с безопасным, понятным и документированным обходом; решение фиксируется явно.
- **P3:** визуальная полировка и необязательные удобства.

Функционально готовый срез: все включённые P0/P1 закрыты, обязательные сценарии 02–05 воспроизводимы, ограничения доступны до действия пользователя, независимое ревью принято. Окончательно готовый срез дополнительно проходит 06. Сами эти черновики не присваивают проекту ни один из этих статусов.
