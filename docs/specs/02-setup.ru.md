# 02. Установка и настройка без обходных путей

Статус: черновик. Зависимость: 01. [Общие правила](README.md).

## Пользовательский результат

Пользователь получает артефакт **нашего форка**, устанавливает его в отдельный DSH profile, задаёт свой Ocean, входит, выбирает роль и достигает готовности к подтверждению устройств. Не требуется менять TypeScript, обращаться к внутренним RPC вручную, править generated bundle или запускать наши private fixture scripts.

Настройка должна работать без LLM API key. Добавление модели — отдельный шаг, не скрытая предпосылка remote connection.

## Сценарии

### Новый пользователь

1. Проверяет требования к SDK/Node/сети и выбирает отдельный профиль.
2. Получает локальный/версионированный артефакт форка из документированного источника.
3. Устанавливает и запускает Host; видит фактический server URL, роль и auth state.
4. Входит на собственный Ocean; делает то же на Client.
5. Открывает discovery и панель ключей; далее следует 04.
6. Перезапускает приложение: server/role/auth associations сохраняются, данные не заменяются defaults.

### Ошибка или конфликт конфигурации

Пользователь понимает, что именно не применяется: read-only/CLI overlay, другой writer, несовместимый SDK, ошибочный URL или вход. Введённые несекретные значения сохраняются для исправления. Пароль не восстанавливается в поле и не попадает в лог.

## Требования

- **SET-01. Идентичность дистрибутива.** Страница установки/CLI показывают origin форка, версию и build/commit. Нельзя выдавать upstream npm-пакет за нашу сборку. До публикации собственного канала допускается проверенный локальный артефакт.
- **SET-02. Безопасная изоляция.** Документированный путь создаёт новый профиль/данные без перезаписи рабочего DSH и без неявного импорта provider credentials. Установка idempotent: повтор не дублирует entry и не ротирует identity.
- **SET-03. Явный сервер.** Нет неявного fallback к авторскому cloud. Валидация схемы URL/нормализации, понятная ошибка TLS/доступности. Не вводить URL с credentials; secrets передаются отдельным защищённым способом. Insecure HTTP допустим лишь как явно обозначенный локальный dev-режим, не как default для сетевого доступа.
- **SET-04. Рабочая запись настроек.** После Save применённые значения совпадают с показанными. UI отличает persisted, runtime-only и overridden values; не сообщает об успехе, если overlay сохраняет старую effective config. При конфликте сообщает источник и безопасный путь изменения; обход приоритета конфигурации запрещён.
- **SET-05. Применение.** Для каждого поля заранее видно «применится сейчас» или «нужен restart». Смена server/role закрывает старые authority/соединения, не смешивает origins, pins и credentials. После неуспеха состояние явно определено, не выглядит успешным.
- **SET-06. Auth.** Ошибки неверных credentials, недоступности и отозванного устройства различаются безопасными сообщениями. Logout очищает/отзывает именно заявленную область и сообщает о частичном удалённом отказе. Повторный submit не создаёт конфликтующие transitions.
- **SET-07. Доступный интерфейс.** Account status, сервер, роль, connect, keys и ошибки достижимы для поддержанного способа установки. Не зависеть исключительно от native Plugins card, которая может отсутствовать для ordinary entry.
- **SET-08. CLI.** Help/status/login/register/logout имеют стабильные exit codes, корректно закрывают stores/resources. Команды не оставляют writer lease после обычного завершения. Ограничения параллельного CLI/Native отражены явно; status не должен представляться безопасным read-only, если он фактически мутирует identity.
- **SET-09. Эксплуатационный старт.** Пользователь понимает, должен ли Host работать постоянно и как запустить/остановить его штатно. Не создавать глобальный autostart или root unit без отдельного выбора.
- **SET-10. Secrets.** Секреты не печатаются в process arguments, логах, export/debug views, Web Storage или URL, кроме необходимого native process-bootstrap механизма, который обрабатывается приватно и не публикуется. Saved password UI не требуется; сохранённые device credentials защищены правами хранения.

## Состояния и минимальный контракт UI

`не настроен` → `сервер задан` → `вход выполняется` → `авторизован` → `готов к trust/connect`.

Независимые индикаторы: effective server/role, auth status и доступность Host. Network failure не превращается автоматически в logout; revoked/invalid auth не маскируется статусом «offline». Отсутствие provider model key не считается ошибкой Ocean auth.

Результат операции сохраняемых настроек должен содержать applied/persisted значения, область применения и необходимость restart либо структурированный отказ. Точная форма API определяется после аудита, не задаётся предположением о native SDK.

## Приёмка

- **SET-AC1:** второй проверяющий проходит чистый Host+Client setup по публичной инструкции без private scripts и ручного RPC.
- **SET-AC2:** после restart совпадают server/role, device identity и auth association; незаданный server не обращается к upstream.
- **SET-AC3:** покрыты invalid URL/TLS, wrong password, unreachable, unsupported SDK, CLI overlay conflict и duplicate submit.
- **SET-AC4:** ordinary entry/bundle способы, включённые аудитом, имеют доступные controls; непринятые варианты явно исключены из инструкции.
- **SET-AC5:** до/после подтверждено отсутствие изменений в рабочем profile и его credentials; secrets отсутствуют в отчёте.

## Не входит

Новый account SaaS/SSO, перенос рабочих ключей, изменение native DSH глобально, отдельный красивый onboarding/redesign. Инструкции и базовые состояния должны быть понятны уже сейчас.
