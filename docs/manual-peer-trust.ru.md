# Ручное доверие новым устройствам

Новые ключи больше не получают доверие автоматически — ни на Host, ни на Client. Авторизация аккаунта на Ocean по-прежнему обязательна, но **сама по себе не даёт доступ к DSH**. Для первого соединения нужны два локальных подтверждения, затем обычный повтор Connect/Retry.

## Порядок

1. Откройте локальный DSH Web на обеих машинах. Поддержанный проверенный вариант — native DSH 0.2.0-rc.2, loopback `127.0.0.1`, обычный пользователь. Работающий профиль не нужно менять для теста: используйте [отдельные HOME/DSH_HOME](dsh-ocean-acceptance.ru.md).
2. Войдите на собственный Ocean и выберите нужный Host на Client. Список устройств только показывает проверенную аккаунтную принадлежность: просмотр **не закрепляет ключи**.
3. Первая попытка соединения остановится. На Client нажмите **«Ключи»** внизу боковой панели; имя кнопки для accessibility — «Доверие устройств». Панель доступна и для явно добавленного обычного plugin entry, без установки default remote bundle. Она также остаётся в конфигурации плагина, если native Plugins page показывает его карточку.
4. В секции **Host на другой машине** найдите **«Собственный полный SHA-256»**. Передайте все 64 символа через независимый доверенный канал — например, лично сверив экран или через уже проверенный SSH. Не используйте имя устройства или короткий 48-битный отпечаток как доказательство.
5. В секции **Client на подключающейся машине** сверьте Device ID и полный отпечаток ожидающего Host. Поставьте отметку о независимой сверке и введите **тот самый полный SHA-256 с другого устройства**. Требуется точное значение из 64 символов `0–9, A–F`, без сокращений, пробелов, приведения регистра или автозаполнения. Затем нажмите «Подтвердить ключ».
6. Вручную повторите Connect. Теперь Client уже доверяет Host, но Host отклонит ещё неизвестный Client **до создания Noise-туннеля и привилегированного DSH peer**. Native Remote UI может отдельно запрашивать workspace metadata, поэтому pending на Host иногда появляется уже после первого подтверждения; такой запрос тоже отклонён и не даёт доступа. Новая панель не удерживает и не продолжает прежнюю handshake-попытку.
7. На Host откройте «Ключи». Сверьте ожидающий Client с **собственным Client-ключом подключающейся машины**, а не с её отдельным Host-ключом. Подтвердите полным SHA-256 таким же способом.
8. Ещё раз вручную повторите Connect. Теперь Noise проверит владение именно закреплёнными ключами и откроет разрешённый DSH channel. Подтверждение в панели само не подключается и не повторяет запросы.

Каждая установка может иметь **два разных ключа**: Host — принимающая роль, Client — подключающаяся. Панель специально показывает их отдельно. Имена, platform и origin запроса — только недоверенные подписи. Копирование отпечатка из самого входящего запроса без сверки исходного устройства **не подтверждает личность**.

На свежем native DSH можно закрыть Preview Notice кнопкой Continue и выбрать Configure later в предложении добавить model API key. Для проверки доверия/транспорта вводить ключ LLM или отправлять prompt не требуется.

## Отказы и срок запроса

- Pending существует только в памяти текущей роли/entry/server/identity, максимум пять минут по монотонным часам. Повторы с тем же ключом не продлевают срок. После перезапуска запросите соединение заново.
- Максимум 32 pending, включая уже сохраняемые решения; отдельный ограниченный cooldown снижает повторный спам. Лишние запросы отклоняются, а существующие не вытесняются произвольно.
- Для решения нужны Device ID, текущая generation и точный полный SHA-256. Старые generation, отклонённые, истёкшие и закрытые authority больше не подходят. При смене server/role или logout обновите панель.
- Известный Device ID с другим ключом **не перезаписывается** и не предлагается как обычный новый запрос. Остановитесь и выясните причину. Не удаляйте identity directory ради обхода проверки. Легитимная новая identity должна пройти новое явное подтверждение.
- Ошибка сохранения не помечает запрос успешно подтверждённым. Неопределённый результат после filesystem commit закрывает дальнейшие grants и требует офлайн-сверки, а не автоматического согласия.

## Смена ключа устройства

Если у уже известного Device ID изменился ключ (переустановка, восстановление, потеря диска), соединение блокируется и в строке состояния появляется «Key: changed». Автоматической перезаписи нет — это защита от подмены.

Восстановление без ослабления доверия:

1. Убедитесь по независимому каналу, что устройство действительно переустановлено, а не подменено.
2. На той стороне, где сохранён старый ключ, откройте «Ключи» → **«Снять доверие»** для этого устройства и подтвердите действие.
3. Повторите Connect: запрос снова станет обычным ожидающим подтверждением.
4. Сверьте **новый** полный SHA-256 через независимый канал и подтвердите его как при первом знакомстве — на обеих сторонах.
5. Повторите Connect. Только после обоих подтверждений откроется канал.

Не удаляйте каталог идентичности и не копируйте отпечаток из самого запроса, чтобы «ускорить» восстановление: так проверка теряет смысл.

## Где разрешён approval

Только собственный аутентифицированный **локальный HTTP carrier** DSH: действующая browser-cookie, реальный loopback socket, согласованные Host/listening port/Origin и отсутствие forwarding headers. Встроенная защита native Host/Origin и cookie не отключается.

Native rc.2 **не применяет** дополнительный аргумент `rpc.handle(..., { authority: 'loopback' })`. Поэтому он не используется как доказательство права: RPC fallback получает только readonly trust status, а approve/reject отклоняются. HTTP-контекст создаётся транспортом, не берётся из payload.

UI обращается к локальному HTTP исходным fetch, без remote RPC fallback. Preview-туннель не может обращаться к собственному app port DSH даже при его внесении в allowlist; control prefix запрещён и на других preview ports. `api/bot` allowlist не расширялся для approval. Native trustedHosts, публичный reverse proxy или один лишь loopback-адрес прокси не считаются локальным оператором.

Проверенный SSH operator может открыть тот же loopback port через собственный защищённый forward или выполнить локальный контроль на машине: это уже имеющееся доверенное OS-действие. Не публикуйте такой forward на `0.0.0.0`.

**Граница защиты:** уже доверенный peer с предоставленным произвольным выполнением кода/терминалом либо локальный администратор способен действовать как OS-пользователь. Эта схема не создаёт изоляцию от ранее выданного полного OS-доступа, root или Docker-администратора.

## Старые pins и хранение

Существующие точные pins сохраняются как **legacy: происхождение подтверждения неизвестно**. Они не переименовываются в ручные и не получают новый trustedAt при обновлении имени/platform/membership. Раньше сохранённый полный public key остаётся точным pin; старый короткий fingerprint сохранён только для совместимости, не для нового человеческого подтверждения.

Новые решения имеют отдельную provenance `manual`. Приватные ключи никогда не отправляются в панель. Изменение доверия сериализуется по каноническому каталогу, перечитывает валидный диск и публикует новое состояние только после durable записи. Неизвестный ключ не может молча заменить известный.

Поддерживается **один writer process на identity directory**. Несколько Store объектов внутри него разделяют lane/state/lease. Две независимые DSH-инстанции с общим DSH_HOME/server/role и одновременно работающие старые/новые версии не поддерживаются: используйте разные изолированные homes или остановите прежнюю инстанцию. Это ограничение не затрагивает пары Host/Client на разных машинах с собственными каталогами.

Штатное закрытие освобождает lease; это проверено на реальных тестовых Host и двух Client. После аварии owner lease не крадётся по TTL/PID. При IDENTITY_IN_USE сначала убедитесь, что другая инстанция действительно остановлена. При INDETERMINATE прекратите работу, сохраните закрытую резервную копию и офлайн сверьте identity/peer state с последним достоверным состоянием. Не очищайте lock/marker на работающем процессе и не считайте удаление marker доказательством успешного commit. Автоматического восстановления/перезаписи ключей нет.

Эта приёмка проверяет Linux и указанный native DSH; совместимость всех OS/версий SDK, power-loss durability оборудования и формальный криптографический аудит не заявляются. Генерация LLM, Codex/ACP и терминал не входят в тест.
