# Свой сервер DSH Ocean Remote

## Статус и границы

Это минимальный вариант развёртывания существующего single-account relay, без нового протокола, интерфейса и внешней авторизации. Все устройства используют один аккаунт нашего сервера. OAuth автора не требуется. Перед распространением образа остаётся открытым вопрос происхождения серверного интерфейса: см. [проверку лицензий](license-review.ru.md).

Сервер передаёт зашифрованный трафик, но остаётся частью границы доверия при регистрации новых устройств. Self-hosting не добавляет ручного подтверждения ключей. Встроенный веб-интерфейс показывает устройства, а не удалённый чат. Работать нужно через плагин DSH или совместимый клиент. Открытый сервер поддерживает Relay, но не WebRTC/TURN.

## Развёртывание с HTTPS

Требуются Docker с Compose v2, домен с DNS A/AAAA на сервер и доступные извне TCP 80/443. Удалите некорректную AAAA-запись, если IPv6 не работает. Порты должны быть свободны; если уже есть reverse proxy, используйте исходный compose.yaml и подключите его к существующему HTTPS-прокси вместо второго Caddy.

Из корня клона:

```sh
cd apps/server
cp .env.example .env
chmod 600 .env
```

В `.env` задайте:

```dotenv
DSH_SERVER_ACCOUNT=owner@example.com
DSH_SERVER_PASSWORD=REPLACE_WITH_A_UNIQUE_RANDOM_PASSWORD
DSH_REMOTE_DOMAIN=remote.example.com
```

DSH_REMOTE_DOMAIN — только DNS-имя, без https://, порта и пути. Пароль — уникальный, случайный, желательно от 24 символов (runtime требует минимум 12). Для защиты от интерполяции Compose пароль с `$` запишите в одинарных кавычках. Примеры не являются рабочими учётными данными. Не коммитьте `.env`, не присылайте его содержимое и полный вывод `docker compose config` в чат.

```sh
docker compose -f compose.ocean.yaml config --quiet
docker compose -f compose.ocean.yaml up -d --build
docker compose -f compose.ocean.yaml ps
```

Используйте **только** compose.ocean.yaml, не объединяйте с compose.yaml: новый вариант не публикует порт Node, наружу доступны лишь 80/443 Caddy. HTTPS-сертификат получает Caddy; public URL сервера автоматически равен `https://DSH_REMOTE_DOMAIN`. Переменные DSH_SERVER_HOST/PORT/PUBLIC_URL из исходного примера в этом варианте не задают внешние параметры. Контейнер relay использует непривилегированного пользователя node из существующего Dockerfile.

Проверка после запуска:

```sh
curl --fail https://remote.example.com/healthz
```

Ожидается JSON со status=ok. Это лишь проверка доступности HTTP, не приёмка зашифрованного соединения. Теги базовых образов пока плавающие: перед production-релизом зафиксируйте проверенные digest и проверьте их лицензии.

## Подключение

1. На bigpc в настройках Remote явно сохраните адрес `https://remote.example.com`, затем войдите с нашим аккаунтом и паролем. Оставьте разрешение управления включённым только на компьютере-хосте.
2. На ноутбуке сохраните тот же адрес, войдите в тот же аккаунт и выключите управление этим устройством и удалённый терминал, если ноутбук должен быть только клиентом.
3. Выберите bigpc, откройте существующую сессию. Отдельно проверьте историю, отправку сообщения, переподключение, файлы и терминал с правами обычного пользователя.

В форке адрес по умолчанию **пока остаётся адресом автора**, включая несколько fallback в UI/CLI. Сам факт установки форка не переключает сервер. На каждом устройстве требуется явная настройка. Не используйте Linux-автоустановщик upstream для пользовательского хоста: он запускает DSH от root.

## Эксплуатация

Данные устройств хранятся в server-data, сертификаты — в caddy-data. Это чувствительные данные; резервную копию server-data делайте при остановленном relay и храните защищённо. Пароль при восстановлении должен соответствовать сохранённой конфигурации. Изменение пароля требует повторной авторизации устройств.

```sh
docker compose -f compose.ocean.yaml stop
# После резервного копирования:
docker compose -f compose.ocean.yaml up -d
```

`down` сохраняет volumes; **не используйте `down -v`**, если не хотите уничтожить состояние и сертификаты. Не запускайте одновременно старый и новый Compose-проекты с ожиданием общей базы: у них могут быть разные имена volumes. Перенос существующего server-data требует отдельной процедуры.

## Проверки этой доработки

Наличие статически корректного Compose-файла не доказывает работу Docker build, выдачу сертификата, совместимость устройств или устойчивость WebSocket. Эти проверки требуют отдельного развёртывания. Текущий шаг не устанавливает плагин и не меняет работающий DSH.
