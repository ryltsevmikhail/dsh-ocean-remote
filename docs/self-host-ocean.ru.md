# Свой сервер DSH Ocean Remote

## Статус и границы

Это минимальный вариант развёртывания существующего single-account relay, без нового протокола и внешней авторизации. Все устройства используют один аккаунт нашего сервера. OAuth автора не требуется. На этапе 2 прежний заимствованный серверный интерфейс заменён минимальной консолью Ocean без старых изображений и стилей. Это не заменяет проверку LICENSE/NOTICE зависимостей и готового образа: см. [проверку лицензий](license-review.ru.md).

Сервер передаёт зашифрованный трафик, но остаётся частью границы доверия при регистрации новых устройств. Self-hosting не добавляет ручного подтверждения ключей. Встроенный веб-интерфейс показывает устройства, а не удалённый чат. Работать нужно через плагин DSH или совместимый клиент. Открытый сервер поддерживает Relay, но не WebRTC/TURN.

## Развёртывание с HTTPS

Требуются Docker с Compose v2, домен с DNS A/AAAA на сервер и доступные извне TCP 80/443. Удалите некорректную AAAA-запись, если IPv6 не работает. Порты должны быть свободны; если уже есть reverse proxy, используйте исходный compose.yaml и подключите его к существующему HTTPS-прокси вместо второго Caddy.

Из корня клона:

```sh
cd apps/server
cp .env.example .env
chmod 600 .env
```

В `.env` задайте:

```dotenv
DSH_SERVER_ACCOUNT=owner@example.com
DSH_SERVER_PASSWORD=REPLACE_WITH_A_UNIQUE_RANDOM_PASSWORD
DSH_REMOTE_DOMAIN=remote.example.com
```

DSH_REMOTE_DOMAIN — только DNS-имя, без https://, порта и пути. Пароль — уникальный, случайный, желательно от 24 символов (runtime требует минимум 12). Для защиты от интерполяции Compose пароль с `$` запишите в одинарных кавычках. Примеры не являются рабочими учётными данными. Не коммитьте `.env`, не присылайте его содержимое и полный вывод `docker compose config` в чат.

```sh
docker compose -f compose.ocean.yaml config --quiet
docker compose -f compose.ocean.yaml up -d --build
docker compose -f compose.ocean.yaml ps
```

Используйте **только** compose.ocean.yaml, не объединяйте с compose.yaml: новый вариант не публикует порт Node, наружу доступны лишь 80/443 Caddy. HTTPS-сертификат получает Caddy; public URL сервера автоматически равен `https://DSH_REMOTE_DOMAIN`. Переменные DSH_SERVER_HOST/PORT/PUBLIC_URL из исходного примера в этом варианте не задают внешние параметры. Контейнер relay использует непривилегированного пользователя node из существующего Dockerfile.

Проверка после запуска:

```sh
curl --fail https://remote.example.com/healthz
```

Ожидается JSON со status=ok. Это лишь проверка доступности HTTP, не приёмка зашифрованного соединения. Теги базовых образов пока плавающие: перед production-релизом зафиксируйте проверенные digest и проверьте их лицензии.

## Подключение

1. На bigpc в настройках Remote явно сохраните адрес `https://remote.example.com`, затем войдите с нашим аккаунтом и паролем. Оставьте разрешение управления включённым только на компьютере-хосте.
2. На ноутбуке сохраните тот же адрес, войдите в тот же аккаунт и выключите управление этим устройством и удалённый терминал, если ноутбук должен быть только клиентом.
3. Выберите bigpc, откройте существующую сессию. Отдельно проверьте историю, отправку сообщения, переподключение, файлы и терминал с правами обычного пользователя.

В плагине Ocean **нет сервера по умолчанию**: установочные конфигурации, Desktop UI и TUI больше не подставляют адрес автора. До настройки адреса Remote не подключается к серверу. Уже сохранённые настройки не стираются: при обновлении с upstream обязательно проверьте адрес в существующем профиле — ранее сохранённый адрес остаётся явной конфигурацией.

Для CLI задайте адрес переменной окружения (это не сохраняет его в профиль DSH):

```sh
export DSH_REMOTE_SERVER=https://remote.example.com
ds-harness-remote status
```

Для TUI задайте ту же переменную при запуске DSH либо serverUrl в настройках активного профиля. Отдельный CLI читает только DSH_REMOTE_SERVER, а не профиль. Его login пока поддерживает QR/OAuth и не добавляет вход по паролю: для минимального self-hosted сервера без QR используйте вход по паролю в плагине DSH. Протокол авторизации этим этапом не изменён.

Изменения этого этапа относятся к плагину и CLI; отдельные Android, VS Code и браузерный клиенты, а также установщик upstream ещё содержат собственные значения по умолчанию и не подготовлены к выпуску Ocean. Не используйте Linux-автоустановщик upstream для пользовательского хоста: он запускает DSH от root.

## Эксплуатация

Данные устройств хранятся в server-data, сертификаты — в caddy-data. Это чувствительные данные; резервную копию server-data делайте при остановленном relay и храните защищённо. Пароль при восстановлении должен соответствовать сохранённой конфигурации. Изменение пароля требует повторной авторизации устройств.

```sh
docker compose -f compose.ocean.yaml stop
# После резервного копирования:
docker compose -f compose.ocean.yaml up -d
```

`down` сохраняет volumes; **не используйте `down -v`**, если не хотите уничтожить состояние и сертификаты. Не запускайте одновременно старый и новый Compose-проекты с ожиданием общей базы: у них могут быть разные имена volumes. Перенос существующего server-data требует отдельной процедуры.

## Проверка production-артефакта без Docker

Из корня репозитория, с Node 22 и pnpm 9.15.4:

```sh
pnpm --filter @dsh-remote/protocol build
pnpm --filter @dsh-remote/server check
pnpm --filter @dsh-remote/server build
mkdir -p .local
node apps/server/scripts/package-server.mjs .local/server-release
node apps/server/scripts/smoke-deploy.mjs .local/server-release
```

Каталог назначения должен быть **новым**, его родитель — существующим. Упаковщик не заменяет ранее собранный/установленный сервер и отказывается копировать в исходные деревья, включая symlink-алиасы родителя. Он копирует только dist, внутренний protocol, ws и zod; версии и отсутствие новых зависимостей проверяются. Не используйте обычный `pnpm deploy`: в этом workspace pnpm 9 дополнительно затягивает зависимости корневого плагина.

При build создаются полные лицензии проекта и 7 проверенных сторонних пакетов, в том числе scheduler 0.23.2 из ReactDOM, а не другой scheduler из корня workspace. Они входят в артефакт и доступны по ссылке «Лицензии» в консоли. Обновление версий или добавление optional peers требует повторной лицензионной проверки; до этого build должен отказать.

Smoke запускает только временный loopback-сервер со случайным паролем и отдельным временным состоянием, проверяет public assets/notices, вход/выход, HTTP Cookie и запрет cross-site API, регистрацию, отсутствие plaintext secrets на диске, сохранение device credential и сброс активной web-сессии после перезапуска. Сервер и временные данные очищаются и при SIGTERM/SIGINT. Это не установка DSH, не проверка браузерной Cookie-политики/HTTPS и не проверка контейнера. Для проверки Docker нужны отдельные build/run, права USER node, volume, healthcheck и длительный WebSocket.

## Проверки этой доработки

Наличие статически корректного Compose-файла не доказывает работу Docker build, выдачу сертификата, совместимость устройств или устойчивость WebSocket. Эти проверки требуют отдельного развёртывания.

Этап удаления неявного сервера (2026-10-19): зависимости установлены только в клоне форка через pnpm 9.15.4 с --frozen-lockfile --ignore-scripts; сборка packages/**, проверка типов плагина, 55 файлов / 396 тестов и verify-dsh-plugin прошли. Проверен собранный CLI: без адреса возвращает ошибку настройки без fetch; оба install patch и публикуемые GitHub bundle не содержат адреса сервиса автора. Независимое read-only ревью diff не выявило ошибок. Проверки выполнены на локальном Node 26.12.0, а не на целевом Node 22 из Dockerfile. Живая Desktop UI, реальное межмашинное соединение и Docker пока не проверены. Плагин не установлен в работающий DSH; его настройки и службы не менялись.
