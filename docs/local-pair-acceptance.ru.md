# Приёмка на одной машине: плагин против локального Ocean

Проверка показывает, что плагин работает с **собственным сервером** без Tailscale и без второй машины: вход в аккаунт, регистрация устройства, список устройств и выход. Вторая машина нужна только для проверки самого соединения Host↔Client.

## Что понадобится

- Собранный сервер (`pnpm --filter './apps/server' build`) и собранный плагин (`cd packages/plugin && pnpm build`).
- Запуск сервера на loopback: заполнить `apps/server/.env` (`DSH_SERVER_ACCOUNT`, `DSH_SERVER_PASSWORD` не короче 12 символов, `DSH_SERVER_PUBLIC_URL`, `DSH_SERVER_DATA_FILE`) и выполнить `cd apps/server && node --env-file=.env dist/main.js`.
- Два изолированных профиля DSH с плагином в `dsh.profile.bundles`, каждый в своём каталоге (см. [установку](fork-install.ru.md)).
- Локальный сервер Ocean на loopback с тестовым аккаунтом.

## Порядок

1. Поднимите локальный сервер на `127.0.0.1` с временным `state.json` и тестовым аккаунтом.
2. В профиле Host задайте `role: host` и `serverUrl: http://127.0.0.1:<порт>`, запустите DSH.
3. Войдите тестовыми данными через control-маршрут: `POST /ds-harness-remote/host.account.login` с `{email, password}` и cookie локальной сессии. Клик по форме в браузере этой проверкой не покрыт — UI-путь описан в [матрице](audit/02-matrix.ru.md) как «частично».
4. В профиле Client задайте `role: client`, тот же `serverUrl`, запустите и войдите теми же данными.
5. Запросите список устройств у Client: `POST /ds-harness-remote/devices` — должен появиться Host.
6. Выйдите из аккаунта у Client.

## Результат прогона

| Шаг | Результат |
| --- | --- |
| Вход Host через плагин | Успешно; в статусе (`status`) появляется `deviceId`, то есть устройство зарегистрировано |
| Вход Client через плагин | Успешно |
| Список устройств у Client | Показывает зарегистрированный Host с `deviceId`, `name`, `platform`, `online`, `lastSeenAt`, версиями |
| Выход | Успешно; после выхода в статусе нет аккаунта |
| Ошибки страницы | Не участвует: проверка идёт через control-маршрут |

## Попытка проверить соединение на одной машине (неудачная)

Следующий шаг — соединить два локальных профиля через тот же локальный сервер — **не удался**, и это зафиксировано как дефект A-53.

Что наблюдалось на одном прогоне:

| Факт | Значение |
| --- | --- |
| Устройства на сервере | два: `client …303b…`, `host …2462…` |
| Собственный `deviceId` в статусе Host-профиля | `…24b4…` — **другого устройства, которого нет на сервере** |
| Список Host'ов у Client | показывает серверное `…2462…` |
| Подключение Client к `…24b4…` | отклонено `MEMBERSHIP_REQUIRED` (такого устройства нет в аккаунте) |

То есть локальный Host-профиль считает себя одним устройством, а на сервере зарегистрировано другое. Причина не установлена: это может быть следствием входа Client (который регистрирует owned-role Host) или повторной регистрации того же аккаунта. До выяснения соединение Host↔Client на одной машине **не заявляется проверенным**; оно проверялось ранее на двух реальных машинах.

## Границы

- Проверено на loopback: Tailscale, реальные сетевые задержки и вторая машина не участвовали.
- Соединение Host↔Client (Relay, доверие ключей, сессия, обрыв) эта проверка **не покрывает**; попытка сделать это на одной машине упёрлась в A-53.
- Модель не вызывалась.
