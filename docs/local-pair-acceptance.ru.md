# Приёмка на одной машине: плагин против локального Ocean

Проверка показывает, что плагин работает с **собственным сервером** без Tailscale и без второй машины: вход в аккаунт, регистрация устройства, список устройств и выход. Вторая машина нужна только для проверки самого соединения Host↔Client.

## Что понадобится

- Собранный сервер (`pnpm --filter './apps/server' build`) и собранный плагин (`cd packages/plugin && pnpm build`).
- Запуск сервера на loopback: заполнить `apps/server/.env` (`DSH_SERVER_ACCOUNT`, `DSH_SERVER_PASSWORD` не короче 12 символов, `DSH_SERVER_PUBLIC_URL`, `DSH_SERVER_DATA_FILE`) и выполнить `cd apps/server && node --env-file=.env dist/main.js`.
- Два изолированных профиля DSH с плагином в `dsh.profile.bundles`, каждый в своём каталоге (см. [установку](fork-install.ru.md)).
- Локальный сервер Ocean на loopback с тестовым аккаунтом.

## Порядок

1. Поднимите локальный сервер на `127.0.0.1` с временным `state.json` и тестовым аккаунтом.
2. В профиле Host задайте `role: host` и `serverUrl: http://127.0.0.1:<порт>`, запустите DSH.
3. Войдите тестовыми данными через control-маршрут: `POST /ds-harness-remote/host.account.login` с `{email, password}` и cookie локальной сессии. Клик по форме в браузере этой проверкой не покрыт — UI-путь описан в [матрице](audit/02-matrix.ru.md) как «частично».
4. В профиле Client задайте `role: client`, тот же `serverUrl`, запустите и войдите теми же данными.
5. Запросите список устройств у Client: `POST /ds-harness-remote/devices` — должен появиться Host.
6. Выйдите из аккаунта у Client.

## Результат прогона

| Шаг | Результат |
| --- | --- |
| Вход Host через плагин | Успешно; в статусе (`status`) появляется `deviceId`, то есть устройство зарегистрировано |
| Вход Client через плагин | Успешно |
| Список устройств у Client | Показывает зарегистрированный Host с `deviceId`, `name`, `platform`, `online`, `lastSeenAt`, версиями |
| Выход | Успешно; после выхода в статусе нет аккаунта |
| Ошибки страницы | Не участвует: проверка идёт через control-маршрут |

## Соединение на одной машине: что проверено

После того как обе стороны подтвердили ключи, соединение Client → Host на локальном сервере действительно устанавливается.

| Шаг | Результат |
| --- | --- |
| Первое подключение без доверия | Отклонено `PEER_APPROVAL_REQUIRED` |
| Подтверждение Host на стороне Client | Успешно (сверен полный SHA, полученный от Host) |
| Повторное подключение до подтверждения на Host | Отклонено (`ok: false`), режим остаётся `local`, у Host появляется запрос (`pending: 1`) |
| Подтверждение Client на стороне Host | Успешно |
| Подключение после обоих подтверждений | `connected`, транспорт `Relay` |
| Host в списке устройств | `online: true` |
| Интерфейс в браузере | Показывает «Remote mode · <host>», выбранный `host-workspace`, транспорт `Relay`; после перезагрузки страницы удалённый режим сохраняется |
| Ответ `status` из браузера | `mode: remote`, `connected: true`, `transport: Relay` |
| Список workspace на Host | Успешно (0 workspace в чистом профиле) |
| Открытие workspace на Host | Успешно: каталог зарегистрирован, режим остаётся `remote`, workspace выбран |

### Ловушка с идентификаторами (важно)

В профиле Host **два разных `deviceId`**:

- `status.deviceId` — идентичность клиентской части этого профиля (используется для локального режима и списка Host'ов);
- `status.host.deviceId` — устройство, которое реально зарегистрировано на сервере в роли Host.

Подключаться нужно ко второму. Если взять первый, сервер отвечает `MEMBERSHIP_REQUIRED`, потому что это устройство роли Client, а соединение Client→Client запрещено. Первая версия этой проверки сделала именно так и получила ложный вывод «идентичность не совпадает»; ошибка была в проверке, не в продукте.

### Ранее заподозренное «connected до подтверждения» — не подтвердилось

Промежуточная версия проверки показывала подключение до одобрения на Host. Причина оказалась в самой проверке: `mode.set` возвращал `ok: false` без исключения, а скрипт считал это успехом. Повторный точный прогон: до одобрения `ok: false`, `mode: local`, `connected: false`, у Host висит запрос; после одобрения — `connected`, `Relay`. Поведение корректное.

### Что осталось непроверенным

- Сессия, история и инструменты через удалённый Host на loopback: цепочка `harness.remote.*` работает (список и открытие workspace прошли), но полноценная сессия требует вызова модели и согласования.
- Обрыв соединения и автоматическое переподключение на loopback не проверялись — логика покрыта юнит-тестами.
- Создание **сессии** в интерфейсе на loopback отдельно не проверялось: после подключения страница уже показывает выбранный workspace, а сценарий с сессией покрыт двухмашинной приёмкой. Модель при этом не вызывалась.

## Границы

- Проверено на loopback: Tailscale, реальные сетевые задержки и вторая машина не участвовали.
- Соединение Host↔Client (Relay, доверие ключей, сессия, обрыв) эта проверка **не покрывает**; попытка сделать это на одной машине упёрлась в A-53.
- Модель не вызывалась.
