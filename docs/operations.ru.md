# Эксплуатация: обновление, откат, резервные копии, удаление

Документ описывает только этот форк и проверенные процедуры. Каждый шаг выполняется в отдельном профиле: рабочий DSH, его ключи и данные не затрагиваются.

Изолированный профиль — это каталог с `DSH_HOME` и `XDG_*`. Его установка описана в [инструкции](fork-install.ru.md).

## Что где хранится

| Данные | Где | Нужны для |
| --- | --- | --- |
| Идентичность устройства и закреплённые ключи | `<DSH_HOME>/remote/servers/<hash>/<role>/` | доверие между устройствами |
| Учётные данные Ocean | там же: `server-credentials.json` — **токены в открытом виде** (файл 0600) | вход на сервер |
| Конфигурация профиля | `<DSH_HOME>/profiles/<имя>/` | настройки плагина и bundles |
| Состояние сервера Ocean | `state.json` в каталоге данных сервера (в Docker-стенде — `/data`) | устройства аккаунта, хэши токенов |

`<hash>` — производная от адреса сервера, поэтому один профиль может помнить несколько серверов.

## Обновление

1. Остановите DSH с этим профилем (один процесс на каталог идентичности).
2. В клоне: `git fetch --tags && git checkout <тег или коммит> && pnpm install`, затем соберите плагин: `cd packages/plugin && pnpm build`.
3. Обновите зависимости профиля: `npm install --omit=dev --ignore-scripts --legacy-peer-deps` в каталоге профиля.
4. Запустите DSH той же командой и проверьте `diagnostics`: версия плагина и `schemaVersion` должны быть ожидаемыми.

**Не проверено:** переход между двумя разными версиями на живой паре устройств. Сборка плагина и установка зависимостей профиля проверены в приёмке установки, не в процедуре обновления.

## Откат

Откат — это тот же путь с прежним тегом:

1. Остановить процесс.
2. `git checkout <прошлый тег>`, `pnpm install`, затем `cd packages/plugin && pnpm build`.
3. Переустановить зависимости профиля (`npm install …` в каталоге профиля) и запустить.

Ключи и доверие при откате не меняются: каталог идентичности остаётся на месте. Если старая версия не понимает новое состояние — восстановите копию из резервной копии (ниже) вместо ручной правки файлов.

## Резервная копия и восстановление

**Сначала остановите DSH.** В каталоге идентичности живёт lease `.identity-owner` и маркер `.identity-indeterminate`; архив, снятый на работающем процессе, после восстановления приведёт к отказу «каталог занят» и потребует отдельного восстановления.

Копируйте целиком каталог данных профиля, не отдельные файлы:

```
tar -C <каталог с DSH_HOME> -czf dsh-home-backup.tgz dsh
```

Восстановление:

1. Остановить процесс.
2. Распаковать архив поверх (`tar -C <каталог> -xzf dsh-home-backup.tgz`).
3. Запустить DSH и проверить `diagnostics`.

**Проверено:** копия, удаление каталога данных, восстановление из архива и повторный запуск сохраняют идентичность устройства (тот же префикс `device.idPrefix`) и состояние плагина. Каталог `dsh/` в проверке удалялся полностью, после восстановления DSH запустился и ответил на `diagnostics`.

Копия содержит секреты (учётные данные, ключи). Храните её там же, где хранили бы ключи: не в общих каталогах, не в репозитории, не в публичных облаках.

## Удаление форка и профиля

1. **Отзовите устройство.** Доступны два пути: из самого устройства (выход в плагине) либо владельцем из консоли Ocean — кнопка «Отозвать» на странице устройств. После отзыва устройство не может подключиться.
2. Остановите процесс DSH для этого профиля.
3. Удалите каталог профиля, который вы создали для теста или работы: в нём `dsh`, `workspace`, `xdg`, `os-home`, `codex-home`.
4. Если в профиле был сохранён сервер: убедитесь, что каталог `<DSH_HOME>/remote` удалён вместе с профилем — в нём идентичность и закреплённые ключи.
5. Проверьте в консоли Ocean, что отозванное устройство больше не подключено.

Удалять рабочий профиль DSH для «очистки» не нужно: форк живёт в собственном профиле.

**Проверено:** остановка, удаление каталога данных профиля и отсутствие остатков после удаления; резервная копия, снятая на остановленном процессе, восстановила идентичность. **Не проверено:** отзыв с самого устройства и отзыв во время живой сессии на двух машинах (в консоли отзыв проверен на локальном стенде).

## Если процесс DSH был убит (аренда каталога идентичности)

Плагин держит аренду каталога идентичности (`.identity-owner`) и **не отбирает её по PID или возрасту файла** — это защита от второго writer'а. После `kill -9`, падения питания или контейнера, убитого вместе с процессом, файл остаётся, и новый запуск не сможет использовать идентичность.

Как это выглядит: DSH стартует, в журнале появляется `remote plugin started without a usable identity {"code":"IDENTITY_IN_USE"}`, а карточка Remote показывает объяснение с указанием файла. Раньше в этой ситуации плагин снимал свой control-маршрут при отказе старта, и интерфейс выглядел как «плагин не работает» без причины — теперь маршрут остаётся и объясняет состояние.

Восстановление (только когда **ни один** процесс DSH с этим `DSH_HOME` не работает):

1. Убедитесь, что процессов нет. Надёжнее смотреть не только по имени: `pgrep -af dsh` и проверьте, что среди них нет процесса с вашим `DSH_HOME` (переменная окружения процесса видна в `ls -l /proc/<pid>/environ` приблизительно; проще — не запускать второй экземпляр и закрыть первый штатно).
2. Удалите файл аренды в каталоге идентичности: `<DSH_HOME>/remote/servers/<hash>/<role>/.identity-owner`, если сервер задан; если `serverUrl` не задан, каталог идентичности — `<DSH_HOME>/remote/.identity-owner`.
3. Запустите DSH снова и проверьте `status` (его отдаёт карточка Remote) и `diagnostics`: `startupError` отсутствует, в снимке диагностики нет `startup.code`.

**Проверено на изолированном профиле:** процесс, убитый `SIGKILL` после получения аренды, оставляет файл; следующий запуск показывает `IDENTITY_IN_USE` в статусе и интерфейсе; после удаления `.identity-owner` запуск восстанавливается, идентичность и Device ID сохраняются. Автоматического отбора аренды нет и не планируется.

## Проверка состояния

- Плагин: карточка «Настройка Remote» → «Скопировать диагностику» (без секретов).
- Сервер: `GET /healthz` и `GET /ready` отвечают 200.
- Консоль: список устройств показывает актуальные online-состояния и роли.

## Чего пока нет

Обновления «одной кнопкой», автоматического отката и автоматического резервного копирования нет: это ручные процедуры. См. [аудит](audit/02-matrix.ru.md).
